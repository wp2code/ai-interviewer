# AI 自动面试机器人 · 架构设计文档

> 场景：招聘方批量筛选 | 形态：软件实时语音面试 | 技术栈：Python / FastAPI 全栈
> 版本：v1.0 ｜ 配套代码见 `app/`，测试见 `tests/`

---

## 0. 一句话结论

这个系统的难点**不在"让机器人说话"**，而在四个地方：

| 难点 | 为什么难 | 解法 | 代码位置 |
|---|---|---|---|
| 轮次控制 | 抢话 / 抢答 / 冷场，体感崩掉 | 事件驱动状态机，端点与打断分离建模 | `app/domain/turn.py` |
| 追问策略 | 固定题库 = 模板化面试，信度极低 | LLM 只抽信号，确定性引擎做决策 | `app/domain/strategy.py` |
| 评分可信度 | HR 一质疑就崩，无法申诉 | 证据锚定 + 档位行为锚点 + 置信度 | `app/domain/scoring.py` |
| 成本结构 | 直觉会指导你优化错的地方 | ASR 占 96%，LLM 只占 2% | 见 §7 |

## 1. 分层架构

```
┌───────────────────────────────────────────────────────────┐
│ ① 接入层    浏览器 WebRTC 端 │ FastAPI 会话网关 │ 打断与端点控制 │
├───────────────────────────────────────────────────────────┤
│ ② 实时链路  流式 ASR      │ 回合决策 + LLM │ 流式 TTS       │
├───────────────────────────────────────────────────────────┤
│ ③ 评估风控  证据抽取      │ Rubric 评分   │ 一致性与红旗    │
├───────────────────────────────────────────────────────────┤
│ ④ 数据运营  Postgres+对象存储 │ 人工复核工作台 │ 监控与成本    │
└───────────────────────────────────────────────────────────┘
              ↑ 校准回流：人工复核结果 → rubric/权重迭代
```

**分层铁律**（代码已强制）：

- `app/domain/` —— 纯逻辑，零 I/O，零网络。可穷举测试、可回放。
- `app/adapters/` —— 只在这里碰外部世界。LLM / ASR / TTS 全部走 Protocol 接口。
- `app/session.py` —— 只做编排与状态维护，不含业务规则。
- `app/main.py` —— 只做协议转换。

> 判断一个文件该放哪：**它能不能在断网的情况下被单测覆盖？** 不能，就说明抽象漏了。

## 2. 轮次控制：把「端点」和「打断」分开

### 2.1 为什么必须分开

很多实现把二者混成一个「静音检测」，结果是候选人插话时机器人还在念稿 —— 面试体感直接崩。而这两个信号的**时间尺度完全不同**：

- **端点检测**：静音持续多久 → 判定"候选人说完"（时间维度，阈值 ~700ms）
- **打断检测**：检测到人声 → 判定"候选人在插话"（能量维度，阈值 ~320ms 持续）

### 2.2 状态机

```
        START
          │
          ▼
     ┌─────────┐  BOT_SPEECH_DONE  ┌──────────┐
     │ GREETING├───────────────────►│ LISTENING│◄──┐
     └─────────┘                    └────┬─────┘   │
          ▲                             │         │
          │ SPEECH_STARTED(打断)         │SPEECH_ENDED
          │                             ▼         │
          │                      ┌──────────┐    │
          └──────────────────────┤ THINKING │    │
                BOT_SPEECH_DONE  └────┬─────┘    │
                                     │MOVE_READY │
                                     ▼           │
                              ┌──────────┐       │
                              │ SPEAKING ├───────┘
                              └────┬─────┘
                                   │BUDGET_EXHAUSTED
                                   ▼
                             ┌──────────┐
                             │ CLOSING  │──BOT_SPEECH_DONE──► ENDED
                             └──────────┘
```

### 2.3 关键参数与理由

| 参数 | 默认值 | 理由 |
|---|---|---|
| `silence_end_ms` | 700 | 中文语速下，700ms 静音基本确认说完。太短会抢话，太长会冷场 |
| `min_speech_ms` | 250 | 咳嗽、咂嘴、键盘声不构成一轮 |
| `barge_in_min_speech_ms` | 320 | "嗯嗯"这种语气词不算插话，否则机器人被自己的回声切掉 |
| `barge_in_grace_ms` | 400 | 机器人刚开口 400ms 内不响应打断 |
| `max_turn_ms` | 90s | 单轮硬上限，防止跑飞 |
| `total_budget_ms` | 25min | 硬约束，触发后强制收尾 |

### 2.4 一个真实踩过的坑：ASR 与端点的竞态

**ASR 收尾信号与 VAD 端点是两条独立信号链**，存在竞态 —— ASR 结果可能先于端点判定到达。若此时直接丢弃转写，**整轮回答就丢了**。

代码里 `_on_utterance_final` 允许在 `LISTENING` 态直接接收转写并进入决策，而不是只在 `THINKING` 态处理。这个 bug 是集成测试（`tests/test_integration.py`）逼出来的，不是拍脑袋想出来的。

## 3. 追问策略：LLM 只抽信号，决策交给规则

### 3.1 架构决策

**不让 LLM 直接输出"下一个问题"。** 三个理由：

1. **不可测** —— 没法写单测，回归全靠人工体验
2. **不可复盘** —— 同一场面试重跑两次，问的题不一样，没法定位问题
3. **不可审计** —— HR 问"为什么问我这个"，答不上来

所以拆成两层：

```
候选人回答
    │
    ▼
┌─────────────────┐   LLM 只干这一件事
│  抽取层 (LLM)    │   从回答里抽结构化信号：
│  extract_signals │   命中哪些维度 / 回答深度 / 是否空洞
│  extract_evidence│   是否前后矛盾 / 有无量化
└────────┬────────┘
         │  AnswerSignals（纯数据，可序列化）
         ▼
┌─────────────────┐   纯函数，可穷举测试
│  决策层 (规则)    │   基于信号 + 覆盖度 + 时间预算
│  StrategyEngine  │   → Decision(kind, dimension, depth, reason)
└────────┬────────┘
         │  Decision
         ▼
┌─────────────────┐   LLM 只干这一件事
│  话术层 (LLM)    │   把 Decision 的意图写成自然口语
│  compose_question│   不暴露策略标注
└─────────────────┘
```

`Decision.reason` 字段记录**为什么问这个** —— 这是给 HR 和给审计看的。

### 3.2 决策优先级（短路执行）

| 优先级 | 条件 | 动作 | 理由 |
|---|---|---|---|
| 1 | 剩余时间 ≤ 收尾尾窗 | 收尾 | 硬约束，不可被覆盖 |
| 2 | 检测到前后矛盾 | 钻矛盾点 | 信息密度最高，优先级 0.95 |
| 3 | 回答空洞 / 复述题干 | **换角度重问**（不加深度） | 深挖空洞答案只会得到更空洞的答案 |
| 4 | 当前维度覆盖未达标 | 沿阶梯深挖 | 正常路径 |

### 3.3 同维度追问阶梯

```
depth 0  主问题        给定情境，看整体轮廓
depth 1  个人贡献      你做了哪部分？他人分别负责什么？
depth 2  取舍依据      备选方案是什么？为什么放弃了其他方案？
depth 3  反思与边界    哪一步最可能出错？重来会怎么改？
```

阶梯的意义：**level 1 是注水者的照妖镜**。真正做过的人能立刻说出"我负责 X，他人做 Y"；没做过的会含糊过去，此时不升级深度，而是回到优先级 3 换角度重问。

### 3.4 维度选择公式

```
缺口(维度) = 权重 × (1 − 覆盖度)
覆盖度     = 0.6 × 深度达成比 + 0.4 × min(证据条数/2, 1)
门槛维度额外 × 1.5
```

**门槛维度**（问题解决、技术深度）无论权重高低都必须问到 —— 否则会漏掉硬伤。

## 4. 评分引擎：产出证据链，不是黑箱分数

### 4.1 三问原则

每个分数必须能回答：

1. **依据哪句原话？** → `Evidence.quote` + 时间戳，可回听
2. **对应 rubric 哪一档？** → `RubricLevel.anchor` 行为锚点
3. **有多确信？** → 置信度，且置信度本身有来源

答不上这三点，HR 一质疑就崩盘 —— 用 AI 做初筛最怕这个。

### 4.2 Rubric 五档

| 档 | 标签 | 行为锚点（判定依据） |
|---|---|---|
| 1 | 不合格 | 仅有结论无过程，关键问题答非所问 |
| 2 | 待改进 | 能复述流程或术语，追问一层就露底 |
| 3 | 合格 | 有清晰个人动作与结果，经得起两轮追问 |
| 4 | 优秀 | 有量化结果、明确取舍逻辑、主动暴露风险 |
| 5 | 卓越 | 指出体系性缺陷并给出系统性方案 |

档位由**加权平均 `level_hint`** 后取最近档位得出，权重考虑来源可信度与理由完整度。

### 4.3 置信度公式

```
置信度 = 0.25 + 0.30×证据充分度 + 0.20×档位一致性 + 0.25×平均证据质量

证据充分度 = min(1, 证据条数/2)
档位一致性 = 1.0（档位差≤1）否则 1 − 0.35×(档位差−1)
证据质量   = 有量化数字(0.4) + 有行为动词(0.35) + 长度足够(0.25)
```

**为什么要有"证据质量"这一项**：一句"我们一起做了个系统"（证据质量 0.15）和一句"我把接口延迟从 800ms 降到 120ms"（证据质量 1.0），不该有同等可信度。

### 4.4 一致性与红旗（确定性规则，不依赖 LLM）

| 检测项 | 规则 | 严重级 |
|---|---|---|
| 数值矛盾 | 同一指标跨轮次相差 ≥ 2 倍 | high |
| 我 vs 我们 | 集体人称占比过高 → 个人贡献边界不清 | medium |
| 口头禅密集 | > 3 处/百字 | low |
| 回答过短 | < 40 字 | low |

**2 倍阈值不是随便定的**：1.5 倍 vs 4 倍是量级差异（真矛盾），2 倍 vs 2.1 倍往往只是统计口径差异。阈值太松会产生红旗噪音 —— **一旦 HR 忽略所有红旗，整个风控体系就废了**。

指标名从数字前方的词典回溯识别（延迟/耗时/成功率…），否则"接口延迟从200ms"与"延迟是500ms"会被当成两个不同指标，矛盾检测直接失效。

### 4.5 推荐档位

| 条件 | 结论 |
|---|---|
| 总分 ≥ 72 且无 high 级红旗 | `advance` 建议进入下一轮 |
| 总分 ≥ 60 | `hold` 建议人工复核 |
| 其余 | `reject` 建议淘汰 |

每个 high 级红旗额外扣 6 分并压低置信度。

## 6. 延迟预算

**目标：候选人说完 → 机器人开口 < 1.2s**（超过 2s 面试体感就明显卡顿）

| 环节 | 预算 | 手段 |
|---|---|---|
| VAD 端点判定 | 700ms | 静音阈值，这是最大头 |
| ASR 收尾 | 150ms | 流式增量解码，句末即刻出结果 |
| LLM 首 token | 300ms | 流式输出 + Prompt 缓存 + 短 schema |
| LLM 生成 | 200ms | 追问话术很短，限制 60 字 |
| TTS 首包 | 100ms | 流式 TTS，句子级合成 |
| 传输 | 50ms | 就近部署 |

**优化杠杆按影响排序**：

1. **降低 `silence_end_ms`** —— 直接砍掉最大头，但过高会抢话。可动态调整：候选人语速快时降到 550ms，慢时升到 850ms
2. **LLM 流式 + Prompt 缓存** —— 系统提示和简历部分命中率很高
3. **并行化** —— 抽证据与生成话术并行（代码中已用 `asyncio.create_task` 实现）

## 7. 成本模型

### 7.1 单场成本（25 分钟 / 12 轮）

| 项 | 计算 | 金额 | 占比 |
|---|---|---|---|
| LLM 输入 | 12 轮 × 3500 tok × ¥2/M | ¥0.084 | 1.5% |
| LLM 输出 | 12 轮 × 700 tok × ¥8/M | ¥0.034 | 0.6% |
| **ASR** | 25 分钟 × ¥0.22/分钟 | **¥5.500** | **96.2%** |
| TTS | 12 轮 × 45 字 | ¥0.097 | 1.7% |
| **合计** | | **¥5.715** | 100% |

对比人工初筛约 ¥60/场 → **节省 90.4%**，**10 场回本**。

### 7.2 降本杠杆（按影响幅度）

| 手段 | 单场 | 变化 |
|---|---|---|
| **ASR 自建部署**（算力摊销 ¥0.03/分） | ¥0.965 | **−83.1%** |
| ASR 降价至 ¥0.12/分 | ¥3.215 | −43.7% |
| LLM 换低价模型 | ¥5.664 | −0.9% |
| 轮次 12→9 | ¥5.661 | −0.9% |
| 上下文压缩 3500→1800 | ¥5.674 | −0.7% |

### 7.3 ⚠️ 反直觉结论

**ASR 占 96.2%，LLM 只占 2.1%。**

大多数团队第一反应是"换个更便宜的模型"，但那**最多省 1%**。真正的杠杆在 ASR：

- 自建部署（FunASR / Paraformer / Whisper + GPU）直接省 83%
- 或与 ASR 供应商谈阶梯价

组合优化后 **¥0.898/场**，1 万候选人仅 **¥0.90 万**。

### 7.4 并发模型

单场实时语音独占 1 条会话流。目标 100 并发 →

- 100 条 ASR 流（ASR 通常按并发连接计费，不是按时长）
- 100 个 LLM 上下文
- 100 条 TTS 流
- LLM 出口带宽 ≈ 200 QPS（首 token 500ms 预算）

**成本与并发强相关**：ASR 若按"并发连接数 × 时长"计费，闲时挂着的连接也在计费 → 需要**会话池 + 空闲回收**。

## 8. 合规红线（招聘场景必看）

| 项 | 要求 | 实现 |
|---|---|---|
| **知情同意** | 面试开始前明确告知"这是 AI 面试官，正在录音"，取得同意 | 开场白必须包含，并记录同意时间戳 |
| **数据最小化** | 只收音频 + 转写，不收视频、不做人脸识别 | 不采集摄像头 |
| **自动化决策告知** | 招聘属于"对个人权益有重大影响的自动化决策"，必须告知并提供人工复核 | `hold` 档 + 人工复核工作台 |
| **人工复核通道** | AI 结论不能是唯一依据 | 报告可覆写，覆写记录留档 |
| **保存期限** | 转写与录音设 TTL（如 90 天）自动删除 | 定时任务 |
| **可解释与申诉** | 候选人有权知道"为什么我被判为 hold" | 每条证据带原话 + 时间戳，可回听 |
| **反歧视** | 不把性别、年龄、婚育、籍贯、口音作为评分特征 | 评分只看 `competency` 维度 |

### 8.1 尤萨案例的教训

2025 年美国 EEOC 起诉两家企业使用 AI 筛选工具，构成对求职者年龄歧视。**核心风险点**：面试中常被问到的问题（如"你打算什么时候要孩子"）本身就是歧视载体，AI 只是让它规模化了。

**设计对策**：候选人普遍会掩盖此类问题以免被淘汰，但**回答本身仍是信号** —— 建议这类话题的转写标记为"敏感维度"，单独人工复核，不进自动评分。

## 10. 风险清单

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| **模板化面试**（所有人同一套问题） | 高 | 信度崩塌 | 追问阶梯 + LLM 适配简历语境 |
| **AI 评分不被 HR 认可** | 高 | 项目停摆 | 人工复核工作台 + 校准集 + 证据可回听 |
| **抢话 / 冷场** | 中 | 体感差 | 状态机 + 参数可调 + 线上监控静音时长分布 |
| **合规风险** | 中 | 法律风险 | 知情同意 + 最小化 + 人工复核 + 敏感维度拦截 |
| **ASR 对口音/方言识别差** | 中 | 误判 | 关键指标人工复核；积累纠错数据微调 |
| **成本随并发线性上升** | 中 | 毛利下滑 | ASR 自建 + 会话池空闲回收 |
| **LLM 生成不当话术** | 低 | 体验差 | schema 约束 + 话术审核 + 敏感词过滤 |

## 12. 目录结构

```
app/
  domain/
    turn.py        轮次状态机 + 端点检测（纯逻辑）
    rubric.py      能力模型 + 评分档位 + 追问阶梯
    strategy.py    追问策略引擎（确定性决策）
    scoring.py     评分引擎 + 红旗检测
  adapters/
    llm.py         LLM 协议 + Mock + OpenAI 兼容实现
  session.py       会话编排
  main.py          FastAPI + WebSocket
web/index.html     浏览器端（Web Speech + Web Audio VAD）
tests/
  test_turn.py             状态机行为测试（10 项）
  test_strategy_scoring.py 策略与评分测试（11 项）
  test_integration.py      端到端集成测试（2 项）
  ws_smoke.py              WebSocket 协议冒烟
```
